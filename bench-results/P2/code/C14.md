# C14: FilterEval SEPARATE mode

## What changed
`FusionOperatorBenchmark.FilterEval.Mode.EVAL_ONLY` was renamed to `SEPARATE`. It now builds both the WHERE predicate
and the EVAL projection through `EvalMapper.toEvaluator` with fusion enabled, which is what commit 3's
`LocalExecutionPlanner.planFilter` does. Setup asserts that both factories are `FusedExpressionEvaluatorFactory`.
Before this change, `EVAL_ONLY` built the predicate unfused, so the commit-3 baseline was too slow.
The Mode javadoc now says: OFF = main, SEPARATE = commit 3 (two operators, each fused), FILTER_EVAL = commit 4.

Both predicates fuse on their own (`a*2+b>40` and `x*y>1.5`). The self-test asserted this for both shapes.

The fix was squashed into commit 4 with `--fixup` and an autosquash onto 251d667d2d77. There are still 4 commits.
- Old tip: 466fcf0510df
- New tip: 23862e77db22 ([ESQL] Fuse WHERE combined with a following EVAL)
- Diff from the old tip: only FusionOperatorBenchmark.java, +24/-11
